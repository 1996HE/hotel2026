## 1. 目的

白馬を訪れる国内外の旅行者に対し、客室、参考料金、宿泊案内、周辺観光・交通、スキー場情報を日中英3言語で分かりやすく提示し、予約リクエストへ案内する。若年層、友人グループ、カップル、家族が、スマートフォンでも短時間で滞在候補を判断できることを目的とする。

## 2. v0.4の範囲

- 方案1「Alpine Pulse」を基準とした視覚プロトタイプ
- スクロール型トップページと6つの独立ページ
- 日本語、中国語、英語の即時切替
- 実際の空室と客室番号を日程から検索する予約画面
- 複数客室の同時選択と、客室ごとの人数・全宿泊者情報
- 日別単価、客室小計、整单総額の表示と送信時価格固定
- 送信から24時間の客室保留と、期限切れ時の自動解放
- 管理画面での整单確認、または理由必須の整单拒否
- 受付・確認・拒否・取消・期限切れの三言語メール通知
- 安全な取消リンクによる、チェックイン72時間前までの自助取消
- 申請番号と申請時メールアドレスによる予約照会
- 照会結果からの理由付き・再確認必須の全体取消
- 同一送信元の照会失敗5回に対する15分間の一時制限と、情報の存在を漏らさない共通エラー
- Cloudflare Turnstileの正式環境必須化
- PC、タブレット、スマートフォン対応
- 生成画像を使用した統一ビジュアル

オンライン決済は本版に含めない。個人Gmailによる送信設定は一時保留とし、SMTP認証情報を登録するまでメール送信は無効のままとする。将来の公開配備時には共用送信アカウントへ切り替える。SMTPアカウント、送信元・管理者メール、Turnstileキーは環境変数で後から設定し、ソースコードへ保存しない。

## 7. 予約リクエスト画面

### 7.1 入力と見積

| 区分   | 項目                                       |
| ------ | ------------------------------------------ |
| 日程   | チェックイン、チェックアウト               |
| 条件   | 複数の具体的客室番号、客室ごとの人数       |
| 宿泊者 | 全員の氏名、成人・子ども区分、子どもの年齢 |
| 代表者 | 氏名、メール、電話、国・地域               |
| 任意   | 要望・備考                                 |
| 同意   | 予約リクエスト確認目的の情報利用同意       |

子どもは年齢を必須とし、料金は成人と同額で計算する。現行の客室別基本料金・日付別料金ルールを1名1泊単価として、各泊・各室の明細と合計を表示する。

### 7.2 申請ライフサイクル

1. 客室IDを昇順にロックし、全室の重複・有効性・定員を同一トランザクションで再確認する。
2. 全室が利用可能な場合のみ、申請番号を発行し、料金を固定して `pending` 予約を作成する。
3. 1室でも競合した場合は整单を保存せず、客人へ再選択を求める。
4. `pending` は通常予約と同様に空室検索から除外し、24時間の期限まで在庫を保留する。
5. 管理者確認時は整单の全明細を `booked` に変更し、顧客・入金初期レコードを作成する。
6. 管理者拒否時は理由を必須とし、全明細を `cancelled` にして在庫を解放する。
7. 期限までに確認されない申請は毎分の定期処理で `expired` にし、全室を解放する。
8. 客人の取消は安全トークンのハッシュ照合または申請番号・メールアドレス照合で行い、理由入力と明示的な再確認後にチェックイン72時間前まで許可する。

### 7.3 状態

| 申請状態    | 意味                                  |
| ----------- | ------------------------------------- |
| `pending`   | 24時間保留中、管理者確認待ち          |
| `confirmed` | 管理者確認済み、各客室予約は `booked` |
| `rejected`  | 管理者が理由付きで整单拒否            |
| `expired`   | 24時間を超過して自動解放              |
| `cancelled` | 客人が安全リンクから期限内に整单取消  |

### 7.4 メールとTurnstile

- 申請時の選択言語 `ja` / `zh` / `en` で客人向け通知を生成する。
- 受付メールには申請番号、日程、固定金額、取消リンクを含める。
- 確認、拒否、取消、期限切れ時も客人と管理者へ通知する。
- メール無効時は予約処理を止めず記録のみ残し、設定後に送信を有効化する。
- v0.4では個人GmailのSMTP設定を一時保留する。送信機能は環境設定が完了するまで無効とし、照会・取消の成否に影響させない。
- 正式配備では `TURNSTILE_REQUIRED=true` とし、サーバー側で必ず検証する。

## 8. 予約照会・セルフサービス取消

### 8.1 照会入力と画面導線

- `/stay/booking` は未ログインで利用でき、日本語、中国語、英語の表示に対応する。
- 必須入力は「予約申請番号」と「申請時のメールアドレス」の2項目とする。
- ヘッダーの共通導線と予約送信成功画面の導線から予約照会画面へ移動できる。
- 予約送信成功画面は申請番号を明示する。メールアドレスや予約情報をURLクエリに含めない。
- 申請番号は前後空白を除去して大文字化、メールアドレスは前後空白を除去して小文字化したうえで照合する。

### 8.2 照会API

| 項目           | 仕様                                                                                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| エンドポイント | `POST /api/stay/bookings/lookup`                                                                                                                                                               |
| リクエスト     | `{ "requestNo": "BR00000001", "email": "guest@example.com" }`                                                                                                                                  |
| 成功レスポンス | `requestNo`、`status`、`checkInDate`、`checkOutDate`、`guestCount`、`totalAmount`、`holdExpiresAt`、`rejectionReason`、`cancellationReason`、`cancellable`、`cancellationCutoffHours`、`rooms` |
| `rooms`        | 客室ごとの `roomNumber`、`roomName`、`guestCount`、`totalAmount`。不要な個人情報は返却しない                                                                                                   |
| 照合失敗       | HTTP 400と `{ "error": "LOOKUP_FAILED" }`                                                                                                                                                      |
| 一時制限中     | HTTP 429と `{ "error": "LOOKUP_RATE_LIMITED" }`                                                                                                                                                |

APIはエラーコードのみを返し、画面は選択言語で安全な案内を表示する。`LOOKUP_FAILED` は照合項目のどちらが誤っているかを示さず、`LOOKUP_RATE_LIMITED` は15分後の再試行だけを案内する。申請番号の存在やメール不一致を画面へ表示しない。

### 8.3 照会結果

| 表示項目   | 表示ルール                                                                                |
| ---------- | ----------------------------------------------------------------------------------------- |
| 基本情報   | 申請番号、チェックイン日、チェックアウト日、合計宿泊者数                                  |
| 客室・料金 | 客室番号、客室名、客室ごとの人数と小計、申請全体の固定合計金額                            |
| 現在状態   | `pending`、`confirmed`、`rejected`、`expired`、`cancelled` を選択言語の人間向け文言で表示 |
| 状態別補足 | `pending` は保留期限、`rejected` は拒否理由、`cancelled` は取消理由を表示                 |
| 取消可否   | 取消可能時は期限と取消ボタン、不可時は理由と宿泊施設への連絡案内を表示                    |

`rejectionReason` は `rejected` の場合のみ、`cancellationReason` は `cancelled` の場合のみ表示する。代表者氏名、連絡先、各宿泊者氏名など、本人が状態確認するうえで不要な個人情報は表示しない。

### 8.4 照会経由の全体取消API

| 項目           | 仕様                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| エンドポイント | `POST /api/stay/bookings/lookup/cancel`                                                                            |
| リクエスト     | `{ "requestNo": "BR00000001", "email": "guest@example.com", "reason": "予定変更", "confirmed": true }`             |
| 成功レスポンス | 取消後の完全な照会結果。`status=cancelled`、`cancellationReason`、`cancellable=false` を含む                       |
| 認証失敗・制限 | 照会APIと同じ `LOOKUP_FAILED` または `LOOKUP_RATE_LIMITED`。画面は不一致項目を明かさず、安全な再試行案内だけを表示 |

- 安全リンク経由の既存 `POST /api/stay/bookings/cancel/{token}` も、リクエスト本文に `{ "reason": "予定変更", "confirmed": true }` を必須とし、取消成功時は完了メッセージを返す。
- どちらの取消経路でも同じ理由・再確認・状態・72時間ルールを適用し、取消理由を申請に保存する。
- 取消理由は前後空白除去後に必須とし、1,000文字以下とする。
- 取消ボタンの実行前に影響範囲と「すべての客室が取消される」ことを表示し、明示的な再確認を必須とする。
- APIは `confirmed=true` でなければ受け付けず、画面だけでなくサーバー側でも取消理由、再確認、照合情報を再検証する。
- `pending` と `confirmed` は、チェックイン日の開始時刻から72時間前までのみ取消できる。取消は関連する全客室に同一トランザクションで適用する。
- `rejected`、`expired`、`cancelled` は読取専用とする。取消期限を超過した `pending` または `confirmed` も読取専用とし、宿泊施設への連絡を案内する。
- 取消成功後は再読込みなしで画面を `cancelled` に更新し、入力された取消理由を表示する。

### 8.5 失敗制限とセキュリティ

- 照会と照会経由の取消は共通の送信元単位カウンターを使用する。形式不正や不一致を含む照合失敗が5回連続した場合、5回目の失敗成立時点から15分間照会と取消を受け付けない。
- 照会成功時はその送信元の連続失敗回数をリセットする。制限期間終了後は再度試行できる。
- 送信元は原則として接続元IPアドレスで識別する。リバースプロキシ配下では、信頼対象として設定されたプロキシからの転送ヘッダーのみ参照する。
- 申請番号とメールアドレスはPOST本文だけで受け取り、URL、通常アクセスログ、クライアント側の永続ストレージに保存しない。
- 照会結果はブラウザやCDNへ保存されないよう `Cache-Control: no-store` を付与する。
- 入力値、照会失敗、取消操作を監視可能な形で記録するが、ログに生のメールアドレス、完全な申請番号、宿泊者情報を含めない。

## 12. v0.4の受入条件

- 9つのURLを未ログインで表示できる
- 日中英切替が全ページで動作し、選択が維持される
- PCとスマートフォンで横方向の崩れがない
- トップの日程検索から予約画面へ条件を引き継げる
- 具体的な複数客室を選択し、各室の人数と全宿泊者を入力できる
- 日別料金明細と整单合計が表示され、送信時に固定される
- 競合時に全室がロールバックされ、二重予約が発生しない
- 管理画面で整单確認、理由付き整单拒否ができる
- 24時間期限切れと72時間前までの安全リンク取消で全室が解放される
- ヘッダーと予約成功画面から予約照会画面へ遷移できる
- 申請番号と申請時メールアドレスをPOSTで照合し、日程、客室、客室別・合計人数、料金、状態、拒否理由または取消理由を表示できる
- 照会と照会経由の取消は連続失敗5回で同一送信元を15分間制限し、エラー文言から予約の存在や不一致項目を判別できない
- `pending` または `confirmed` を、72時間前までに限り、理由入力と明示的な再確認後に整单取消できる
- `rejected`、`expired`、`cancelled` と取消期限超過後は照会のみ可能で、取消操作を表示しない
- 予約照会、照会結果、取消理由、再確認、成功・失敗表示が日本語、中国語、英語で切り替わる
- 公開APIから管理者操作を実行できず、取消トークンはハッシュのみ保存される
- 予約照会と取消のレスポンスは `no-store` で、生の照合値をURLや通常ログへ出力しない
- SMTPが無効でも照会・取消処理は正常完了し、送信未設定により予約状態がロールバックされない
- 実在情報が未確定の箇所に誤った住所・連絡先を表示しない
- クライアントビルド、Javaテスト、視覚比較が成功する

| BL-03 | 汎用エラー           | 存在しない番号、異なるメール、形式不正のいずれも、表示文言から失敗理由を区別できない                     |
| BL-04 | 失敗制限             | 同一送信元の5回目の失敗後から15分間、照会と照会経由の取消を429で拒否する                                 |
| BL-05 | 制限解除・回数初期化 | 15分間後に再試行でき、制限前の正常照会で連続失敗回数がリセットされる                                     |
| BL-06 | 取消正常             | 期限内の `pending` と `confirmed` を、理由と `confirmed=true` 付きで全体取消し、全室を解放する           |
| BL-07 | 取消入力検証         | 理由が空、1,000文字超過、または `confirmed=false`・未指定の場合は一切の状態を変更しない                  |
| BL-08 | 取消不可状態         | `rejected`、`expired`、`cancelled`、72時間期限超過では取消できず、照会は継続できる                       |
| BL-09 | 競合・再送信         | 取消と管理者確認・拒否・期限切れが競合しても、許可された状態遷移は1回のみで部分取消が発生しない          |
| BL-10 | 多言語               | 照会入力、結果、状態、制限、取消、再確認の全文言が `ja`、`zh`、`en` で切り替わる                         |
| BL-11 | 個人情報・キャッシュ | URL、通常ログ、画面の永続保存に照合値が残らず、照会と取消のレスポンスに `Cache-Control: no-store` がある |
| BL-12 | SMTP無効             | Gmail/SMTP未設定でも照会と取消が完了し、メール送信失敗で予約トランザクションが取り消されない             |
| BL-13 | レスポンシブ・操作   | PCと狭幅画面で横スクロールがなく、キーボード操作とフォーカス表示を使用できる                             |
