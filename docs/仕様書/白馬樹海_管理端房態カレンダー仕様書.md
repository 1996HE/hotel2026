# 白馬樹海 管理端房態カレンダー仕様書

**版数**: 1.0
**更新日**: 2026-09-30
**対象**: 管理者専用 `/calendar`、`/api/room-calendar/**` および連動する予約・客室 API

## 1. 目的と適用範囲

管理者が自然月単位で全客室の予約、確認待ち、滞在、販売停止、メンテナンス、当日清掃状態を確認し、同じ画面から必要な操作を完結できるようにする。公開サイトには本画面、内部理由、他客の情報、監査情報を公開しない。

本段階の対象は次のとおりである。

- 客室を行、日付を列とする月間 Tape Chart
- 予約と公開多室申請の表示・詳細・状態操作
- 管理者による単一客室の直接予約
- 単一客室の販売停止・メンテナンス期間
- 全部解除、先頭解除、末尾解除、中間解除（左右への分割）
- 退室後の清掃待ちと清掃完了
- 画面表示中の30秒自動更新

ドラッグによる移動、複数客室の一括新規予約、OTA同期、料金編集、強制超売、WebSocketは対象外とする。

## 3. 唯一の事実源

月ごとの日別房態テーブルは作らない。日历表示は毎回、次のデータから導出する。

| データ                                             | 表すもの                                         |
| -------------------------------------------------- | ------------------------------------------------ |
| `reservations` / `public_booking_requests`         | 客室を使用する予約、状態、公開多室申請のグループ |
| `room_inventory_blocks`                            | 指定期間の販売停止・メンテナンス                 |
| `rooms.occupancy_status` / `rooms.cleaning_status` | 今日時点の物理的な在室・清掃状態                 |

空室は「有効予約も有効在庫ブロックも存在しない」ことから導出する。`rooms` の現在状態を未来日へ展開しない。

## 4. 日付・競合規則

予約、販売停止、メンテナンスはすべて半開区間 `[startDate, endDateExclusive)` とする。

- 10月1日入住、10月3日退房は、10月1日と2日の2泊を占有する。
- 10月3日は次の客が入住できる。
- 重複条件は `existing.start < requested.end AND existing.end > requested.start` とする。
- 販売停止・メンテナンスは公開空室照会、見積、申請確定、管理予約のすべてを遮断する。
- 既存予約と重なる在庫ブロック、既存在庫ブロックと重なる予約を強制作成できない。
- 過去日を新規操作の開始日にできない。

通常表示の優先度は `checked_in > booked > pending > maintenance > stop_sale > vacant` とする。予約と在庫ブロックの不正重複が見つかった場合、優先色だけで隠さず `conflict=true` として警告表示する。

## 5. 画面仕様

### 5.1 月間 Tape Chart

- 自然月の1日から月末までを一画面に表示する。
- 左列は客室番号・名称・定員・当日清掃状態、上段は日・曜日とする。
- 左客室列と日付ヘッダーはスクロール時に固定する。
- 前月、今日、翌月、任意年月を選択できる。
- 今日、週末、過去日は色だけに依存しない表示差を持つ。
- 予約と在庫ブロックは日ごとの重複セルではなく、連続した帯で表示する。
- 月をまたぐ帯は表示月の端で裁断し、矢印で継続を示す。
- 状態は色に加えて文字で表示する。

### 5.2 範囲選択

空セルの最初のクリックを開始日、同じ客室の2回目のクリックを退房日／販売再開日 (`endDateExclusive`) とする。2回目の日付は宿泊・停止期間に含めない。2回目が開始日以前、別客室、既存イベント上、過去日の場合は作成しない。`Esc`、取消、月変更で選択を解除する。

確定後は統一ダイアログから次のいずれかを選ぶ。

1. 直接予約（1回につき1客室、保存後 `booked`）
2. 販売停止（理由必須）
3. メンテナンス（理由必須）

### 5.3 詳細ダイアログ

予約帯をクリックすると必要なときだけ詳細 API を呼ぶ。月間 API には電話、メール、取消トークンを含めない。

- 公開多室申請は全子予約を表示する。
- `pending` は整単確認または理由付き整単拒否のみ許可する。
- 確定済み多室申請は、全室が未入住の場合のみ理由付き整単取消を許可する。
- 入住・退室は選択した1客室単位で実行する。
- 単一予約は理由付き取消を許可する。
- 退室後は客室を `needs_cleaning` にし、清掃完了操作を表示する。
- 清掃待ちは未来予約を妨げないが、同日次客の入住は清掃完了まで拒否する。

在庫ブロック帯をクリックすると、種別・期間・理由の更新と全部／一部解除を行える。中間だけを解除する場合は同一トランザクションで左右2ブロックを生成し、元ブロックを無効化する。

## 6. API仕様

すべて管理者認証とCSRF保護の対象である。

| メソッド | パス                                     | 用途                                       |
| -------- | ---------------------------------------- | ------------------------------------------ |
| GET      | `/api/room-calendar?month=YYYY-MM`       | 客室、表示用予約帯、在庫ブロックを集合取得 |
| GET      | `/api/room-calendar/reservations/{id}`   | 予約、公開申請、全子予約、許可操作を取得   |
| POST     | `/api/room-calendar/blocks`              | 販売停止／メンテナンス作成                 |
| PUT      | `/api/room-calendar/blocks/{id}`         | 楽観ロック付き更新                         |
| POST     | `/api/room-calendar/blocks/{id}/release` | 全部／一部解除、必要時分割                 |
| POST     | `/api/booking-requests/{id}/confirm`     | 公開多室申請を整単確認                     |
| POST     | `/api/booking-requests/{id}/reject`      | 理由付き整単拒否                           |
| POST     | `/api/booking-requests/{id}/cancel`      | 理由付き管理者整単取消                     |
| POST     | `/api/reservations/{id}/check-in`        | 選択客室の入住                             |
| POST     | `/api/reservations/{id}/check-out`       | 選択客室の退室                             |
| POST     | `/api/rooms/{id}/cleaning-status`        | 客室の清掃完了                             |

月間レスポンスは `month`、`monthStart`、`nextMonthStart`、`today`、`generatedAt`、`rooms`、`stays`、`blocks` を返す。期間末尾は API・DB とも `endDateExclusive` の意味を維持する。

エラーは `400`（入力不正）、`401`（未認証）、`403`（権限／CSRF）、`404`（対象なし）、`409`（在庫競合、状態競合、古いversion）、`500`（予期しない障害）に分ける。

## 7. DB・トランザクション

`room_inventory_blocks` は客室、種別、開始日、販売再開日、理由、有効状態、分割元、version、作成・更新・取消情報を持つ。`room_inventory_block_events` は作成、更新、解除、分割の前後値、操作ID、操作者、時刻を追記保存する。

予約と在庫ブロックの書込みは次の順序に統一する。

1. トランザクション開始。
2. 対象 `room_id` を昇順にして `rooms` 行を `FOR UPDATE` でロック。
3. 有効予約と有効在庫ブロックの双方を再確認。
4. 状態、予約、ブロック、監査を同一トランザクションで更新。
5. PostgreSQL exclusion constraint とトリガーを最後の防御として使用。

多室申請の確認・拒否・取消は全件成功または全件ロールバックとする。子予約だけの取消は拒否する。

## 8. 自動更新と同時操作

- 初回表示時に即時取得する。
- `document.visibilityState === "visible"` の間だけ30秒ごとに更新する。
- 非表示から復帰した直後と更新成功後に即時再取得する。
- 古い要求結果は新しい月の表示を上書きしない。
- バックグラウンド更新で入力中フォーム、選択範囲、開いているダイアログを消さない。
- 更新対象が他の管理者に変更された場合は `409` とし、再読込後に再確認を求める。

## 9. 受入基準

| ID     | 受入条件                                                                       |
| ------ | ------------------------------------------------------------------------------ |
| CAL-01 | 未認証利用者は画面・APIへアクセスできず、公開APIに内部房態や他客情報が出ない。 |
| CAL-02 | 選択した自然月を客室行×日付列で完全表示できる。                                |
| CAL-03 | 半開区間により退房日と次の入住日が同日でも競合しない。                         |
| CAL-04 | 予約・確認待ち・入住・販売停止・メンテナンスが連続帯と文字で識別できる。       |
| CAL-05 | 空期間から単一客室予約、販売停止、メンテナンスを作成できる。                   |
| CAL-06 | 予約と在庫ブロックの全入口で重複を拒否し `409` を返す。                        |
| CAL-07 | 多室申請の確認・拒否・取消が整単かつ原子的に完了する。                         |
| CAL-08 | 販売停止／メンテナンスの全部、先頭、末尾、中間解除が正しく反映される。         |
| CAL-09 | 退室後に清掃待ちとなり、清掃前の同日次客入住を拒否する。                       |
| CAL-10 | 過去日は読取専用で、新規予約・新規ブロックを作成できない。                     |
| CAL-11 | 表示中30秒更新、画面復帰時更新、操作直後更新が入力状態を破壊しない。           |
| CAL-12 | 在庫ブロックの全変更に操作者・時刻・前後値が残る。                             |

## 10. 検証方針

- 日付計算はうるう年、月跨ぎ、同日回転、帯の裁断を単体テストする。
- Serviceテストは予約対ブロック、ブロック対ブロック、過去日、分割、状態遷移、清掃を検証する。
- APIテストは認証、CSRF、400/404/409、月間レスポンスの個人情報非露出を検証する。
- PostgreSQL実機で exclusion constraint、トリガー、並行予約対ブロックを検証する。H2だけでDB排他の成功を宣言しない。
- ブラウザで横スクロール、固定列・見出し、日中切替、ダイアログ、30秒更新を確認する。
