# 調査・追加ヒアリング報告書

**作成日**: 2026-07-14  
**対象**: 白馬樹海 民宿管理システム  
**調査範囲**: 宿泊者名簿、個人情報、技術サポート状況、AWS利用条件

## 1. エグゼクティブサマリー

現行システムを予約・客室管理として使うことは可能だが、法定の宿泊者名簿の正本とするには、少なくとも住所・連絡先、該当する外国人宿泊者の国籍・旅券番号、三年保存を実装する必要がある。現行の取消・退房後の物理削除経路は、法定記録と業務データを分離するまで本番で許可すべきではない。また、アプリ内認証がなく全APIが `permitAll` のため、社外到達可能な状態での本番運用は不可である。

外部SaaSへの業務依存は確認されなかった。AWSへ移行する場合は、データ保管地域、委託先管理、IAM、暗号化、backup、log保持を社内規程と照合する。

## 2. 調査結果

### 2.1 旅館業法・宿泊者名簿

| 調査項目     | 公式情報からの確認                                       | 本設計への反映                              | 判定       |
| ------------ | -------------------------------------------------------- | ------------------------------------------- | ---------- |
| 名簿項目     | 旅館業法第6条は氏名、住所、連絡先等の記載を求める        | 代表者・同行者に氏名、住所、連絡先を追加    | 必須       |
| 保存期間     | 旅館業法施行規則は宿泊者名簿を3年間保存する規定          | `retention_until`、物理削除禁止、監査を追加 | 必須       |
| 外国人宿泊者 | 日本国内に住所を持たない外国人は国籍・旅券番号を記載     | 条件付き必須項目と旅券写し管理を追加        | 必須       |
| 電子保存     | 厚生労働省は電子的な宿泊者名簿の取扱いを案内             | 検索・提示・CSV出力・backupを設計           | 対応可能   |
| 旅券写し     | 厚生労働省は該当する外国人宿泊者の旅券提示・写し等を案内 | 非公開S3、暗号化、アクセス監査              | 要運用確認 |

公式参照:

- e-Gov 旅館業法 第6条: https://laws.e-gov.go.jp/law/323AC0000000138
- e-Gov 旅館業法施行規則: https://laws.e-gov.go.jp/law/323M40000100028
- 厚生労働省「旅館業法について」: https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/0000130600.html
- 厚生労働省 宿泊者名簿関係案内: https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/0000130600_00001.html

**注意**: 国の法令に加え、施設所在地の自治体条例・保健所運用で追加項目や提示方法が定められる可能性がある。管轄窓口への確認を本番化のPhase 0完了条件とする。

### 2.2 個人情報保護

宿泊者情報、連絡先、旅券情報、アクセス履歴は個人情報として、利用目的の特定、必要最小限の取得、安全管理、委託先管理、保存期間、事故対応を定める必要がある。特に旅券写しは影響が大きいため、画面一覧へ表示せず、権限・短時間URL・暗号化・閲覧監査を必須とする。

漏えい等が発生した場合は、個人情報保護責任者が個人情報保護委員会への報告および本人通知の要否・期限を判断する。アプリ担当だけで独断対応しない。

公式参照:

- 個人情報保護委員会「個人情報の保護に関する法律についてのガイドライン（通則編）」: https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/
- 個人情報保護委員会「漏えい等の対応」: https://www.ppc.go.jp/personalinfo/legal/leakAction/

## 3. 現行仕様とのギャップ

| 優先度   | ギャップ                           | 影響                        | 対応                           |
| -------- | ---------------------------------- | --------------------------- | ------------------------------ |
| Critical | 住所・連絡先・外国人項目がDBにない | 名簿要件を満たせない        | V2 migration、画面/API/CSV追加 |
| Critical | 取消・退房済み予約を物理削除できる | 三年保存違反の可能性        | 論理削除、保持期限、承認job    |
| Critical | 認証なし、API permitAll            | 不正閲覧・変更              | OIDC、RBAC、社内network限定    |
| High     | 定時処理がWeb各instanceで動く      | 重複更新                    | EventBridge/SQS/Worker         |
| High     | 実PostgreSQL CIが不足              | Flyway/排他制約の退行       | Testcontainers CI              |
| High     | backup復元・DLQ運用が未整備        | 復旧不能・処理漏れ          | 四半期演習、Runbook            |
| Medium   | Node/Java build環境の固定不足      | 再現性低下                  | toolchain/CI固定               |
| Medium   | SLA/RPO/RTO未確定                  | AWS構成・費用を確定できない | 顧客合意                       |

## 4. 顧客への追加ヒアリング

### 優先度A — 着手前に必須

1. 本システムを法定宿泊者名簿の正本として使用するか。紙または別システムとの役割は何か。
2. 施設所在地と管轄保健所はどこか。追加項目、様式、提出方法を確認済みか。
3. 既存予約・宿泊履歴の不足住所等を誰がいつ補完するか。補完できない記録をどう承認するか。
4. 利用者、STAFF/MANAGER/ADMINの割当、削除・CSV・旅券閲覧の承認者は誰か。
5. 社内IdP、VPN、AWS account、domain、Slackは利用できるか。外部internetからの利用は必要か。
6. 現行の「完全削除」が必要な業務理由は何か。法定保存対象と分離できるか。

### 優先度B — 設計確定前

1. 最大客室数、年間予約数、同行者数、同時利用者、繁忙期のピークはどれくらいか。
2. 許容停止時間、RPO、RTO、夜間休日の連絡・復旧要否は何か。
3. 外国人宿泊者の旅券写しを保存するか。保存期間、閲覧者、削除承認者は誰か。
4. 名簿CSVの提出先、文字コード、列順、印刷の要否は何か。
5. 現行データの移行日、業務停止可能時間、移行後の照合責任者は誰か。
6. 取消、no-show、日帰り、連泊延長、客室移動、料金訂正の正式な状態遷移は何か。

### 優先度C — 運用開始前

1. Slack channel、当番、重大度、顧客連絡文面、ticket systemをどうするか。
2. backup保持日数、監査ログ保持年数、四半期復元演習の参加者は誰か。
3. 予約サイト、決済、会計、本人確認との将来連携予定はあるか。
4. 多言語、公開予約、複数施設、請求書・領収書の将来計画はあるか。
